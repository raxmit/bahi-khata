# M2.4 Category integrity decision brief

**Status:** Decision approved by user (2026-10-22); implementation and database verification tracked separately  
**Prepared:** 2026-10-22  
**Scope:** Decide transaction/category identity, type mismatch, and rename/delete behavior. No application code, schema, migration, or database was changed or accessed for this brief.

## Current behavior inspected

- Prisma stores `Transaction.category` as a required `String`; it has no relation to `Category`. `Category` has a UUID ID, `name`, `type`, and `isDefault`, with uniqueness on `(name, type)`.
- Transaction create and PATCH business validation checks a nonblank category label, but does not check that a category exists or that its type matches the transaction. The M2.3 PATCH path validates the merged transaction, but its category is still a string.
- Category creation validates uniqueness within type. The API exposes list/create/delete; default categories cannot be deleted. There is no rename endpoint.
- The transaction form filters available category names by selected transaction type. Existing transactions, filtering, and summary breakdowns use the category string.
- The initial migration creates independent `transactions` and `categories` tables. Its seed provides ten default categories. Historical deleted custom categories may therefore appear in transactions with no matching current category.

## Recommended decisions

### 1. Store a stable category ID on each transaction

Use `Transaction.categoryId` as a required foreign key to `Category.id`, with an index. Keep category names and types on `Category`, rather than copying mutable names into transactions. Use a restrictive delete relation (`ON DELETE RESTRICT`): deleting a category must never delete transactions or leave a dangling reference.

At the API boundary, accept `categoryId` for create/update and return it with transactions. Return the current category name as a display field (for compatibility, the response may retain `category` as the resolved name during a transition). Forms submit IDs but render names. Filters and summaries should group by stable ID internally and display the current name. This avoids ambiguous name reuse and ensures renames are reflected consistently.

**Tradeoff:** This requires coordinated migration and API/UI changes. Stable IDs prevent historical records from silently changing identity when a label is reused, and relational integrity lets the backend enforce existence and type. A name-only alternative is smaller but cannot reliably represent rename, same-name cross-type categories, or deleted-category history.

### 2. Reject category/type mismatch on every write

On transaction create or update, require the selected category to exist and have the same `type` as the resulting transaction. Return HTTP 400 with a field-level category error for missing, invalid, or wrong-type category IDs. The check applies to the fully merged PATCH record, so changing transaction type requires selecting a matching category in the same request (or first issuing a valid category change if the current category has that type).

Category type is immutable once created; there is no current category-update endpoint. If a future feature permits type changes, it must reject the change while transactions reference the category, or provide an explicit reassignment workflow. Never silently reinterpret transaction types.

**Tradeoff:** Type changes take an explicit category selection. This keeps income/expense reporting coherent and avoids a category update retroactively changing the meaning of transactions.

### 3. Rename custom categories in place; make deletion reference-safe

- Add rename behavior for custom categories by updating the same category row/ID. Existing transactions keep that ID and display the new name. A `(name, type)` uniqueness conflict returns HTTP 409. Keep default category names immutable to preserve stable seeded defaults.
- Permit deletion of a custom category only when no transactions reference it. If referenced, return HTTP 409 with a clear message and require the user to reassign those transactions to an existing same-type category first. Do not cascade-delete transactions, retain a hidden label, or automatically move records.
- Continue to reject deletion of default categories (HTTP 403, as today).

**Tradeoff:** Reassignment before deletion takes extra user action, but preserves each transaction's explicit classification and makes summaries predictable. Automatic reassignment can change financial reporting without the user noticing.

## Migration and rollback implications

The current transaction category string is the only historical classification evidence. A migration must not guess silently or destructively rewrite it. Proposed additive sequence:

1. Add nullable `categoryId` and its index, preserving the current `category` string as a compatibility/display snapshot.
2. Backfill by exact `(transaction.category, transaction.type)` match to a category with the same name and type. Produce counts and IDs/labels for unmatched or mismatched rows; do not log financial amounts or notes.
3. For any unmatched rows, pause before enforcing constraints. The operator must explicitly map them to same-type categories or create custom categories that preserve their labels. A mismatch must be reviewed rather than coerced.
4. Validate that every transaction maps to one category with matching type. Add the foreign key with `RESTRICT`, then make `categoryId` required only after that check passes.
5. Deploy backend/API compatibility and frontend ID-based selection in an order that does not leave old clients writing names alone. Retire the string snapshot only in a later reviewed migration after rollback compatibility is no longer needed.

No database operation should occur until this mapping policy is approved and the migration is generated/reviewed against a disposable database. Existing persistent data must be inventoried and backed up before migration; a fresh empty-database test does not establish production-data safety.

Rollback before the string snapshot is removed: roll the application back to the version that reads/writes the snapshot, leave the additive column/FK in place if the old Prisma/client version tolerates them, and restore the pre-migration backup if migration integrity is uncertain. After category renames or reassignment writes, rollback to name-only semantics can lose stable identity; therefore retain an ID-to-name audit/export and database backup, and do not drop the compatibility string in this milestone. A destructive down migration that removes mappings is not an acceptable rollback plan.

## Synthetic validation plan (proposed; not run)

Use a newly created disposable MySQL database/Compose project, never a developer or production database. Seed defaults and create two custom categories (`Books` Expense and `Bonus` Income). Create synthetic transactions under both.

| Case | Expected result |
|---|---|
| Create a transaction with an existing same-type category ID | HTTP 201; persisted `categoryId` resolves to that category; response includes its current display name |
| Create with unknown ID, or ID belonging to the opposite type | HTTP 400; no transaction row is written |
| PATCH amount/note only on a valid transaction | Success; category ID, category type, and omitted values remain unchanged |
| PATCH transaction type while retaining a category of the old type | HTTP 400; stored transaction is unchanged |
| PATCH type and category ID together to a same-type category | Success; amount/date/note remain unchanged |
| Rename a custom category used by multiple transactions | Success; category ID remains constant; all associated transactions and summary display the new name |
| Rename to another category's same-type name | HTTP 409; old name and transaction displays remain unchanged |
| Delete an unreferenced custom category | HTTP 204; category absent afterward |
| Delete a referenced custom category | HTTP 409; category and all transactions remain unchanged |
| Delete a default category | HTTP 403; default remains present |
| Backfill exact existing labels/types | Each matching synthetic transaction maps to exactly one category; amount/date/note are unchanged |
| Backfill unmatched label or wrong-type-only match | Migration preflight reports the row and blocks required-FK enforcement until explicitly resolved |
| Repeat migration/startup against already migrated disposable DB | No duplicate categories or mapping changes; schema reports current |
| Restore pre-migration backup after a failed rehearsal | Original transaction/category rows and labels are recovered; record exact restore command and verified counts |

For each rejection, verify HTTP status and database row counts/state, not only the UI message. Verify list, filters, and summary use category IDs for identity and current names for display. Record exact commands and output, applied migration status, and cleanup of the disposable resources.

## Risks and open implementation constraints

- Historical free-text labels may not map to current categories, especially labels left after category deletion; required-FK rollout must stop on unresolved rows.
- Concurrent category deletion/transaction creation can race if existence/type validation is only an application query; the FK protects existence, while type consistency needs a transaction-safe server rule or database design that also constrains type.
- API and UI contract changes touch transaction DTOs, category/transaction repositories, filters, summaries, forms, tests, and potentially clients. Old clients posting names need an explicit compatibility window.
- Category rename changes the displayed label for all historical transactions by design; category-level summaries will also use the renamed label. This must be explicit to users.
- Custom category uniqueness is case/collation sensitive according to MySQL defaults; decide whether case/spacing normalization is needed before adding rename UI. Do not silently normalize existing labels in the migration.
- Migration rollback after writes under ID-based semantics requires backup/audit evidence; a down migration alone cannot reconstruct prior associations reliably.

## Approved behavior and scope

The user approved this proposed behavior and implementation scope on 2026-10-22:

1. Required stable category ID foreign key, with name retained temporarily for migration/API compatibility.
2. Reject missing or wrong-type categories; PATCH validates the resulting transaction and requires a matching category when its type changes.
3. Rename custom categories in place; keep defaults immutable; reject deletion of referenced custom categories until transactions are reassigned; continue blocking default deletion.
4. Implement the additive, preflighted migration and API/UI changes only after synthetic mapping validation; do not run migration against any non-disposable database.

This approval covers local implementation and synthetic validation. It does not approve applying migrations or running database operations against the running Compose stack; request that approval separately before those actions.
