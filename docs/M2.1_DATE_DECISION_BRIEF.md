# M2.1 Date and Timezone Decision Brief

**Status:** Adopted and implemented (2026-10-21).
**M1.9:** Done; its clean-startup and browser/API/MySQL evidence is recorded in [RELEASE_READINESS.md](RELEASE_READINESS.md#m1-9-end-to-end-local-verification).

## Current behavior and risks

- Prisma stores transaction `date` as MySQL `DATE`, which is the right storage shape for a calendar date with no time or timezone.
- At decision time, create/filter DTOs accepted broader ISO strings, and backend future-date checks depended on host-local time. Summary bounds and UI defaults/navigation also mixed host and UTC date behavior. Those issues are covered by the implementation below.
- At decision time, Monday-start weeks, inclusive filter endpoints, and month-clamped weekly buckets lacked one complete documented contract and boundary tests.

## Adopted contract and implementation

Treat transaction dates as **civil dates** end to end: the API accepts and returns only strict `YYYY-MM-DD`; MySQL continues storing `DATE`; calculations compare/calendar-operate on date-only values without converting them to instants. This avoids timezone conversion of the transaction itself.

For “today” and the nonfuture rule, use the adopted explicit application timezone: **`Asia/Kolkata`**. The UI default/max date and backend validation use the same app-calendar date, independent of browser/server host timezone.

Define period rules as follows:

- **Week:** Monday through Sunday (ISO week), inclusive. Use ISO week numbers. A weekly summary reference date selects the week containing that date.
- **Month:** first through last calendar day, inclusive.
- **Year:** January 1 through December 31, inclusive.
- **Monthly weekly breakdown:** ISO Monday–Sunday buckets intersected with the selected month and clamped to month start/end; each date belongs to exactly one bucket.
- **Filters:** inclusive start and end dates; reject invalid calendar dates and `startDate > endDate`.
- **Period navigation:** move to the requested adjacent period without day overflow (use a canonical in-period reference date such as period start; weekly navigation advances exactly seven calendar days).

Tradeoff: a fixed initial app timezone is predictable for a single owner and matches the INR product context, but users who travel or expect device-local “today” may see a different date. A per-account timezone is more flexible, but requires owner settings and an authorization/account design that do not yet exist.

## Edge examples

Under the adopted `Asia/Kolkata` timezone:

| Case | Expected result |
|---|---|
| Instant `2026-10-20T18:45:00Z` (00:15 on Oct 21 in Kolkata) | App “today” is `2026-10-21`; a transaction dated Oct 21 is allowed, Oct 22 is rejected. |
| Monthly summary reference date `2026-03-01` | Bounds are `2026-03-01` through `2026-03-31`; Feb 28 is excluded and Mar 1 included. |
| Weekly reference date `2026-06-01` (Monday) | Bounds are `2026-06-01` through `2026-06-07`; Sunday May 31 belongs to the prior week. |
| Weekly reference date `2026-12-31` | Bounds cross the year boundary as `2026-12-28` through `2027-01-03`; the date is counted once. |
| Monthly breakdown for May 2026 (starts Friday) | First bucket is May 1–3, then May 4–10; final bucket ends May 31. No bucket includes April or June dates. |
| Yearly summary for leap year 2024 | Bounds are `2024-01-01` through `2024-12-31`; Feb 29 is valid and included. `2025-02-29` is invalid. |
| Navigate January 31 forward one month | Selected period becomes February, not March due to date overflow. |
| API date `2026-02-30` or timestamp `2026-10-21T00:00:00Z` for a transaction date | Reject with HTTP 400; transaction dates are strict calendar-date strings, not timestamps. |

## Affected areas

- Backend `CreateTransactionDto`, `FilterCriteriaDto`, `ValidatorService`, `SummaryController`, `SummarizerService`, and any date serialization/helper code.
- Frontend transaction default/max date and validation; dashboard summary reference date; insights reference-date navigation, request formatting, weekly display; transaction/dashboard date display; date filter checks.
- API contract/spec wording and focused backend/frontend tests. Prisma `@db.Date` should remain unchanged; this decision does not propose a schema migration.

## Exact validation cases after the decision

1. Run with a non-UTC host timezone and assert the same injected instant `2026-10-20T18:45:00Z` yields app date `2026-10-21` in both UI and API; Oct 21 is accepted and Oct 22 rejected.
2. Accept canonical valid leap date `2024-02-29`; reject `2025-02-29`, `2026-02-30`, empty input, and a timestamp supplied where a date-only field is required.
3. For summaries, assert monthly bounds for `2026-03-01`, yearly bounds for `2024-02-29`, and weekly bounds for Monday `2026-06-01` and Thursday `2026-12-31` exactly match the examples above.
4. Verify transactions on both inclusive filter endpoints are included; reject reversed `2026-03-02` to `2026-03-01`.
5. For May 2026 weekly breakdown, assert first/last buckets are clamped, each transaction appears once, and weekly totals equal monthly totals.
6. Verify Insights navigation from Jan 31 to February and Feb 29, 2024 to the corresponding 2025 period does not overflow into an unintended month.
7. Verify create/list/read round trips preserve the exact `YYYY-MM-DD` string in MySQL `DATE`, API JSON, UI display, summary, and filters under UTC and non-UTC browser/server settings.

## Material risks

Without a single explicit date policy, users can create an apparent future date, see a transaction under the wrong day/month, or receive totals that differ by host/browser timezone. A changed validation rule may reject timestamp values currently accepted by the backend, although the UI already submits date-only strings. Changing only the UI would leave the API boundary inconsistent. No stored-data migration is expected because the column is already `DATE`, but historical records near period boundaries should be checked with synthetic fixtures before release.

## Decision record

The user adopted strict `YYYY-MM-DD` civil dates, `Asia/Kolkata` for today/future validation, Monday–Sunday ISO weeks, inclusive calendar period and filter bounds, and overflow-safe navigation. Implementation keeps Prisma/MySQL `DATE`; no schema migration was made. This brief now records the adopted policy and its validation evidence.
